体验指引 & 演示脚本

一、这个 Demo 演示了什么

  • 身份即权限：Agent 只认当前客户身份，跨客户订单号会被直接拒绝。
  • 真实数据链路：Agent 通过静态 REST 接口读订单，不靠模型编造。
  • 可执行售后：取消订单、申请退款、催发货等写操作由 Dify 代码节点状态机完成。
  • 政策兜底：7 天无理由、15 天换货、退款时效等回答来自知识库而非拍脑袋。

二、推荐演示动线（约 3 分钟）

  1. 选 张伟（C1001） 作为当前身份，问 AI："我买的东西到哪了？" → Agent 按身份查出运输中订单并给出物流节点。
  2. 继续问："帮我取消 O202609190902" → 待发货订单取消成功，给出退款时效。
  3. 切换身份到 王强（C1003），仍问同一个订单号 → Agent 拒绝，且不透露任何订单字段。这是最能打动面试官的一步。
  4. 切回 张伟，问："那个耳机拆过了还能退吗？" → 命中 7 天无理由政策，并核对签收日期给出结论。

三、常见追问速答

数据从哪来？
预生成的静态 JSON 接口，api/ 目录随仓库发布，Dify 用自定义工具按 OpenAPI 调用。
为什么不用真实后端？
Demo 要能"点开链接就看到"，静态托管零运维；写操作在 Dify 代码节点内做状态机，接口边界清晰，替换成真实后端只需换 Base URL。
API Key 会不会泄露？
不会。浏览器只访问自建代理，Key 只存在代理的进程环境变量里，从不进入前端代码。
Dify 里配置了哪些东西？
意图识别与回复两段提示词、开始节点的身份变量（customer_id / order_id）、HTTP 节点查订单、代码节点状态机、政策知识库。

四、想自己配一套

页面零依赖、零构建，assets/js/config.js 是唯一需要填配置的文件；dify/ 目录下是 Agent 侧的接口定义与售后判定代码。
